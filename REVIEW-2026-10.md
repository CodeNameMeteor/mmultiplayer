**Highest-priority items:**

1. **[S1, Critical, Verified]** Unsynchronized map iteration in `GetClientById`. Any UDP packet can crash the server while players join or leave.
2. **[S2, Critical, Verified]** Lock-order inversion between the ping loop and room disconnect. The whole server can freeze.
3. **[S7, High]** UDP is unauthenticated. Anyone can overwrite another player's position, and replies go to the packet's source address (reflection).
4. **[C1, High]** A player with a long name who is "it" can crash the next client they tag. Names are unbounded on the server and copied into fixed 255-byte `sprintf_s` buffers.
5. **[C3–C7, High]** The client has a cluster of cross-thread races and use-after-free risks. Render and UI threads read state the network thread frees or rewrites, and game objects are touched off the game thread.
6. **[C8, High]** The client overwrites its server address with the source of any UDP datagram it receives.
7. **[C10, High]** The TCP reader treats each `recv` chunk as whole messages. A message split across reads drops the connection and forces a reconnect.
8. **[B1, High]** The installer XOR-obfuscates binaries specifically to avoid Defender, then adds a Defender exclusion. This weakens protection for users.
9. **[S8, High]** Tag mode can be cheated or griefed by any room member, including a freeze that lasts effectively forever.
10. **[S16, Medium, Verified]** The Dockerfile cannot build the server.

## 3. Server (Go)

### S1. Unsynchronized iteration over `room.Clients` crashes the server · Critical · [Verified]

- **Where:** `Server/system.go:23-36` (`GetClientById`), called from `Server/main.go:115-117` for every UDP packet of the right size. The writers are `Server/room.go:33` (`AddPlayer`) and `Server/room.go:133` (`OnPlayerDisconnect`).
- **What:** `GetClientById` takes only the *system* lock and then iterates each room's `Clients` map. The room's own lock is never taken. Joins and leaves write that map under the room lock, so the two run concurrently.
- **Impact:** Any client can send 676-byte UDP packets. Together with normal joins and leaves, this triggers a concurrent map read/write. The goroutine has no `recover`, so the whole process exits.
- **Evidence:** The race detector reported four `DATA RACE` warnings between `GetClientById` (`system.go:28`) and `AddPlayer` and `OnPlayerDisconnect`. The probe then panicked with a nil dereference inside `GetClientById` (`system.go:29`).
- **Fix:** Take the room's read lock inside the loop, or better, keep a single `id → *Client` map guarded by one mutex (this also gives O(1) lookup, see S18).

### S2. Lock-order inversion freezes the whole server · Critical · [Verified]

- **Where:** Ping loop `Server/main.go:36-42` holds `system.RLock()` and calls `room.SendMessage` (room `RLock`). `Server/room.go:124-140` (`OnPlayerDisconnect`) holds the room write lock and calls `system.RemoveRoom` (system write lock, `room.go:136`, `system.go:14-16`).
- **Impact:** Once the last member of a room leaves at the moment the ping loop is iterating, both goroutines block forever. Every later `system.Lock`/`RLock` then blocks too: no new connections, no UDP lookups, no pings.
- **Evidence:** A probe that mirrors these two paths did not finish. A healthy run completes in 20 seconds, and the probe hit its 45-second timeout. The goroutine dump shows goroutine 7 in `RemoveRoom` waiting on `system.Lock`, and goroutine 8 in `Room.SendMessage` waiting on the room `RLock` while holding `system.RLock`.
- **Fix:** Never acquire the system lock while holding a room lock, or the reverse. Snapshot the room list under the system lock, release it, then lock rooms one at a time.

### S3. Second lock cycle: client mutex versus room mutex · High · [Inferred]

- **Where:** Connect, name, level, character, and disconnect handlers hold `client.rwMu` (write) and then take a room lock (`Server/client.go:43-77` → `room.go:30`; `client.go:106`, `client.go:182`, `client.go:217` → room locks). The opposite order occurs in `SendLastPackets`: it holds the room `RLock` (`Server/room.go:263`) and then calls `GetLevelAndPosition` on other clients (`room.go:282-283`, `client.go:229`).
- **Impact:** Go's `RWMutex` blocks new readers once a writer is waiting. So a UDP handler holding room `R` can wait for client `R`, while a client handler holding client `W` waits for room `R` behind a pending room writer. This is a deadlock that depends on timing. It was not reproduced.
- **Fix:** Make the order consistent (for example: room lock first, then client). Or copy the fields needed for the UDP fan-out under the client lock and release it before taking the room lock.

### S4. Unbounded input and no rate limiting · High · [Read]

- **Where:** `Server/client.go:267-285` (`json.Decoder` with no size limit), `client.go:95-141` (names, chat body, announce body, room name are not capped), `client.go:143-153` (cooldown). No connection limit, no rate limit, `room.go:242-245` spawns a goroutine per recipient per message.
- **Impact:** A single client can send one enormous JSON value and exhaust memory, or flood chat. Each chat message is fanned out to every room member.
- **Fix:** Cap message size (for example, `io.LimitReader` or a per-message byte budget), cap name, room, and chat lengths, and rate-limit per connection.

### S5. Slow readers cause unbounded goroutines and memory · Medium · [Read]

- **Where:** `Server/client.go:220-227` (`Tcp.Write` with no write deadline). `room.go:243` and `room.go:257` start one goroutine per recipient per broadcast.
- **Impact:** A client that stops reading but keeps the socket alive (by sending harmless messages, which reset only the read deadline) accumulates blocked writer goroutines and their payloads.
- **Fix:** Set a write deadline, and use a bounded per-client outbound queue with a single writer goroutine.

### S6. Message ordering is not preserved · Medium · [Read]

- **Where:** `Server/room.go:243`, `room.go:257`, and `client.go:47` all use `go c.SendMessage(...)`.
- **Impact:** Messages from one broadcast can arrive out of order. For example, `gameMode`, `tagged`, or `canTag` can be reordered, or `disconnect` can arrive before `connect`. Client state then diverges.
- **Fix:** Use one ordered outbound queue per client (see S5).

### S7. UDP is unauthenticated and replies are reflected · High · [Read]

- **Where:** `Server/main.go:94-127` (no source check, identity is a 32-bit ID). `Server/client.go:82-88` and `room.go:36-42` broadcast every ID to all room members. `main.go:116-122` store the packet as the player's position and bones. `room.go:262-271` reply to `addr` for every other player in the level.
- **Impact:**
  - Anyone who joins a room (rooms are joined by name, with no password) learns IDs and can overwrite any member's position and bones.
  - The reply goes to the packet's source address. Source addresses can be spoofed, so the server can be used to reflect traffic at a third party, with amplification of roughly (players − 1).
  - Tag proximity is computed from these client-supplied positions (`room.go:282-293`), so position injection also cheats tag.
- **Fix:** Authenticate UDP with a per-session token issued over TCP, bind each UDP peer to its TCP session, and only reply to the bound address.

### S8. Tag mode can be cheated and griefed by any member · High · [Read]

- **Where:** `Server/client.go:189-208` (anyone can start, end, or self-report death). `client.go:143-153` and `room.go:103-108` (cooldown is unbounded). `room.go:183-215` (`setTaggedPlayerUnsafe` does not check `canTag` or cooldown). `client.go:203-208` and `room.go:172-181` (self-reported `dead` tags the sender immediately).
- **Impact:**
  - Any player can make themselves "it" at any time by sending `dead`.
  - Setting `cooldown` to a very large value (for example `1e9` seconds) combined with the above makes the tagged player unable to move (the client ignores their input until `canTag`, `Client/addons/client.cpp:879` and `:972`). The countdown is effectively permanent until someone ends the game.
  - `announce` is an arbitrary broadcast body rendered the same as normal chat (`client.cpp:683-694`), so anyone can impersonate a system message. `chat` prefixes the client-supplied name (`client.go:122-125`), so names can be spoofed the same way.
- **Fix:** Make tagging server-authoritative (the server decides death from its own state, not a client message), clamp cooldown to a sane range, and add host or permission concepts for start and end.

### S9. Re-tag race during cooldown · Medium · [Read]

- **Where:** `Server/room.go:286-291`. A goroutine calls `setTaggedPlayerUnsafe` without re-checking `canTag` or `gameMode`, and `room.go:183-215` does not check them either.
- **Impact:** Two proximity events can produce an extra tag during cooldown.
- **Fix:** Re-check the state under the write lock before tagging.

### S10. Re-connecting leaves a ghost in the old room · Medium · [Read]

- **Where:** `Server/client.go:75` overwrites `client.room` without removing the client from the previous room's `Clients`.
- **Impact:** The old room keeps a ghost. The ghost still receives broadcasts, can be tagged (which stalls the game), and keeps the old room from ever being deleted (a leak). The same client ID can then appear in two rooms (see S1, S20).
- **Fix:** Leave the current room before joining another, under the proper locks.

### S11. Join races with the last member leaving · Medium · [Read]

- **Where:** `Server/client.go:65-73` releases the system lock before `AddPlayer` at `client.go:90`.
- **Impact:** If the room is emptied and removed in the window, the joiner is added to an orphaned room. It is silently isolated, and a later joiner with the same name creates a second room with that name.
- **Fix:** Perform lookup and insert under the same lock, or retry on a stale room.

### S12. Unlocked reads of client and room fields · Medium · [Read]

- **Where:** `Server/client.go:82-88` (`room.gameMode`, `taggedPlayerId`, `canTag` read without the room lock). `room.go:266-270` (`c.lastPacket`, `c.level` read without `c.rwMu`). `main.go:125` and `client.go:278` (`client.room` read without `client.rwMu`).
- **Impact:** Data races. Strings and slices are not atomic, so a torn read can crash the process, not just return a stale value.
- **Fix:** Take the appropriate lock, or make these fields immutable after creation.

### S13. Busy loops on persistent accept or read errors · Low · [Read]

- **Where:** `Server/main.go:79-82` (`Accept` error → `continue`), `main.go:106-108` (`ReadFrom` error → `continue`).
- **Impact:** A persistent error (for example, out of file descriptors) spins a core at 100%.
- **Fix:** Back off with a short sleep.

### S14. Log injection and unbounded log content · Low · [Read]

- **Where:** `Server/client.go:71`, `92`, `214`, `281`, `system.go:20`. Client-chosen names and room names are logged raw. `log.Printf` already adds a newline, and the room log line adds another.
- **Impact:** A name containing newlines forges log lines.
- **Fix:** Quote with `%q` and cap the length.

### S15. No transport security or authentication · Medium · [Read]

- **Where:** Plaintext TCP and UDP on port 5222 (`Server/main.go:15`, `70-72`, `97`). No TLS, no tokens, no password on rooms.
- **Impact:** Anyone on the network path can read or inject chat and game traffic. Acceptable for a LAN toy, but a risk for any public deployment.
- **Fix:** Document the trust model. For public use, add TLS on TCP and session tokens (see S7).

### S16. Dockerfile cannot build the server · Medium · [Verified]

- **Where:** `Server/Dockerfile:3` copies only `main.go`. `client.go`, `room.go`, `system.go`, and `go.mod` are not copied, and the build line is `go get -d` (`Dockerfile:4`).
- **Evidence:** Building the single copied file fails with `undefined: System`, `undefined: Room`, `undefined: Client`.
- **Other issues:** `FROM golang` is unpinned. `FROM scratch` runs as root (no `USER`). `go get -d` is deprecated for module builds. No `HEALTHCHECK`.
- **Fix:** `COPY go.mod go.sum ./` and `COPY Server/ ./`, use `go build` with a pinned Go version, and add `USER 65534:65534`.

### S17. Dead code · Low · [Verified by grep]

- `Server/main.go:23-68` and `Server/system.go:11`: the `rng` type and `system.rng` field are set but never read.
- `Server/room.go:26`, `92-94`, `167-169`, `200-203`: `cancelTagCheck` is never assigned a non-nil value.
- `Server/room.go:110-122`: `CurrentTaggedPlayerId` and `IsTaggingEnabled` are unused.
- `Server/room.go:227-232`: `announceUnsafe` is unused.

### S18. Performance: linear lookup and O(N²) fan-out · Low · [Read]

Severity rises to Medium at larger room sizes.

- **Where:** `Server/system.go:23-36` is O(total clients) per UDP packet, under the system `RLock`. `main.go:115` starts a goroutine per packet. `main.go:105` allocates 4 KB per packet. `room.go:262-271` calls `WriteTo` once per peer while holding the room `RLock`.
- **Scale:** The client sends about 60 packets per second of 676 bytes, roughly 40 KB/s upstream. Each client receives (N − 1) × 40 KB/s. At 10 players that is about 360 KB/s per client.
- **Fix:** Index clients by ID (see S1), reuse buffers, and do socket writes outside the lock.

### S19. Cooldown conversion can overflow · Low · [Read]

- **Where:** `Server/client.go:248-254` converts `v * float64(time.Second)` to `time.Duration` with no range check. Large or negative values wrap, which can re-enable tagging immediately.
- **Fix:** Validate and clamp to a range before converting.

### S20. Random 32-bit client IDs can collide · Low · [Read]

- **Where:** `Server/main.go:86` uses `uuid.New().ID()`, which yields 32 bits. Collisions overwrite `room.Clients` entries silently.
- **Fix:** Use a server-side counter, or check for collisions.

### S21. Dependencies and toolchain are dated · Low · [Read]

- `go.mod` declares `go 1.19` and `github.com/google/uuid v1.3.0` (2022). No dependency-update automation is configured.

### S22. Protocol constants are duplicated across languages · Low · [Read]

- Port `5222`, the packet size `676`, the character count, and mode strings such as `"tag"` are duplicated in Go and C++. No protocol version is exchanged, so a mismatched client and server fail silently.
- **Check:** The 676-byte size is consistent. `PACKET_COMPRESSED` is 4 + 12 + 2 + 2 × 329 = 676 bytes (`Client/addons/client.h:12`, `65`).
- **Fix:** Put the protocol in one spec (or shared header) and add a version field to `connect`.

## 4. Client (C++)

### C1. Long names crash other clients via fixed buffers · High · [Read]

- **Where:** `Client/addons/client.cpp:855-875` (the `buffer` at `855` and the `sprintf_s` at `859` and `867`), `:957`, `:1499-1547` (`sprintf_s` into `char[0xFF]`).
- **What:** Names are capped only by the 254-character input field on the client. The server accepts any length (`client.go:95-111`, `43-77`). The formatted message `"[Tag] %s tagged %s"` can exceed 255 bytes.
- **Impact:** The message at `client.cpp:867` is built only on the client that has just become "it" (`client.cpp:853`), and it uses the previous "it" player's name. So a long-named player who is "it" and tags someone crashes that victim. `sprintf_s` then calls the CRT invalid-parameter handler, which by default aborts the process. One malicious name crashes the next player it tags.
- **Fix:** Cap names on the server and client (for example 24 characters), and build messages with `std::string` or truncated `snprintf`.

### C2. Uninitialized stack data sent to the server and chat · Medium · [Read]

- **Where:** `Client/addons/client.cpp:855` declares `char buffer[0xFF]` with no initializer. Lines `863-869` fill it only if the previous tagger is found. Lines `871-874` send it as an `announce` body regardless.
- **Impact:** If the previous tagger is not in the list, stack bytes go to the room as chat.
- **Fix:** Initialize the buffer, or return early when the name is unknown.

### C3. Cross-thread data races in render and UI · High · [Read]

- **Where:**
  - `OnRenderGames` iterates `Players.List` without the lock (`client.cpp:1127`, `1163`) and calls `GetPlayerById` (`1224`).
  - `GamesTab` reads `Players.List.size()` (`1492`) and `UserClient.GameMode` (`1486`, `1539`). `GameMode` is written by the network thread (`366`, `817`). `UserClient.Level` is read by the render thread (`1119`) and written from the game thread (`1654`).
  - `Client::GetPlayerList()` returns raw `Player*` copies without a lock (`client.cpp:79-82`), and `Disconnect` deletes those objects (`client.cpp:271-274`, `796`).
  - Plain `bool` flags such as `IsConnected` and `IsLoading` are written and read across threads with no atomics.
- **Impact:** Use-after-free and torn `std::string` reads when players join or leave while frames are rendering.
- **Fix:** Route all state changes through one thread or one lock. Use `std::atomic<bool>` for flags. Do not hand out raw pointers without a lock.

### C4. Writes under a shared lock · Medium · [Read]

- **Where:** `Players.Mutex.lock_shared()` guards writes in the level handler (`client.cpp:705-729`), character handler (`741-760`), pre-level-load (`1651-1661`), post-level-load (`1668-1680`), pre-death (`1694-1696`), and post-death (`1701-1712`). These set `Actor`, `Level`, `Character`, and `IsLoading`.
- **Impact:** Several readers can hold the shared lock at once, so these writes race with each other and with readers.
- **Fix:** Use the exclusive lock for any write.

### C5. `Disconnect()` runs concurrently from several threads · High · [Read]

- **Where:** Called from the listener loop (`client.cpp:376-378`, `Disconnect()` in the loop increment), the status thread (`434`), and the UI thread (`1367`, `1406`), while the listener thread is still calling `recv` on `TCPSocket` (`167`).
- **Impact:** Double `closesocket`, a socket closed under a blocked `recv`, and concurrent mutation of `Players.List`.
- **Fix:** Make disconnect a request to the network thread, with a single owner for the sockets.

### C6. Game objects are touched off the game thread · High · [Read]

- **Where:** `Engine::SpawnCharacter` correctly queues work (`Client/engine.cpp:771-778`). `Engine::Despawn` does not: it calls `actor->ShutDown()` directly (`engine.cpp:780-784`). It is called from the network thread at `client.cpp:271`, `723`, `752`, and `790`.
- **Impact:** Unreal Engine 3 objects are modified from a thread the engine does not expect. This is undefined behavior and can crash in the game's tick.
- **Fix:** Queue despawns the same way spawns are queued.

### C7. Spawn queue holds a reference into a `Player` that can be freed · High · [Read]

- **Where:** `Client/engine.cpp:47-49` stores `ASkeletalMeshActorSpawnable *&` in the queue. That reference points into `Client::Player::Actor`. The queue is consumed in `engine.cpp:544-556` (the write is at `549`). `Disconnect` (`client.cpp:274`) and the disconnect handler (`796`) delete `Player` objects.
- **Impact:** If a player is deleted between queueing a spawn and the next tick, the tick writes through a dangling reference. The window is narrow but real.
- **Fix:** Queue by player ID, and look the player up when the tick runs.

### C8. The client's server address can be overwritten by any UDP sender · High · [Read]

- **Where:** `Client/addons/client.cpp:291` passes `&Server` as the `from` address to `recvfrom`. `Server` is a global, so each received datagram overwrites it with the sender's address. `OnTick` sends outbound positions to `&Server` (`client.cpp:920`).
- **Impact:** Any host that can reach the client's UDP port can redirect the outbound position stream, and can inject positions for any player by 32-bit ID (`client.cpp:296-310`) with no source check.
- **Fix:** Store the server address separately, and drop datagrams whose source does not match it.

### C9. UDP datagram length is not checked · Medium · [Read]

- **Where:** `Client/addons/client.cpp:291-309`. The return value of `recvfrom` is never compared with `sizeof(packet)`.
- **Impact:** A short datagram leaves part of `packet` uninitialized, and those bytes are copied into `LastPacket`. An oversized datagram is silently truncated.
- **Fix:** Require the exact size and discard anything else.

### C10. TCP framing breaks when a message is split across reads · High · [Read]

- **Where:** `Client/addons/client.cpp:138-186` (`RecvJsonMessage`). Each `recv` chunk is parsed on its own. On a parse failure the function returns `false` (`client.cpp:159-160`). The caller's loop (`client.cpp:441`, `while (RecvJsonMessage(msg))`) treats `false` as a disconnect.
- **Impact:** Whenever a message straddles a read boundary, which becomes common under load, the client drops the connection and reconnects, losing messages. Long messages (see S4 and C1) make this more likely.
- **Fix:** Accumulate bytes in a growing buffer, and parse only complete NUL-terminated messages, carrying the remainder over.

### C11. Settings values are not validated, causing out-of-bounds reads and startup exceptions · Medium · [Read]

- **Where:** `Client/addons/client.cpp:1568` (`get<Engine::Character>()` with no range check) and `:1313` (`Engine::Characters[...]` indexed with that value). `client.cpp:1562-1572` and `Client/addons/trainer.cpp:294-301` call `.get<std::string>()` and `util.h:103-121` call `.at()`. All of these throw on wrong types.
- **Impact:** A hand-edited or corrupt settings file can cause an out-of-bounds read in the menu, or an exception that escapes `Initialize` on the thread started from `DllMain` and crashes the game at injection.
- **Fix:** Validate types and ranges at load, and fall back to defaults with a log message.

### C12. Settings storage is fragile and does excess I/O · Medium · [Read]

- **Where:** `Client/settings.cpp:108-120` (non-atomic write). `settings.cpp:80-99` (any parse failure resets all settings). `settings.cpp:76` (`GetSetting` calls `Save()` on every read). `settings.cpp:8` (one global JSON object used from multiple threads with no lock).
- **Impact:** A crash mid-write, or a single corrupted byte, wipes every setting. Trainer initialization performs dozens of `GetSetting` calls (`trainer.cpp:724-740`, `1665-1677`), each rewriting the whole file.
- **Fix:** Write to a temp file and rename. Only save on change. Guard the global with a mutex.

### C13. Socket and address-info errors · Medium · [Read]

- `Client/addons/client.cpp:391` and the UDP equivalent check `TCPSocket < 0`. `SOCKET` is unsigned, so this is never true. It should compare with `INVALID_SOCKET`.
- `client.cpp:116-123`: the loop advances `result` to `NULL`, so `freeaddrinfo(result)` frees nothing and the list leaks.
- `client.cpp:101`: `WSAStartup` runs on each `Setup()` call with no matching `WSACleanup`. The reference count grows every 500 ms while the server is down.

### C14. Busy loop on UDP receive errors · Low · [Read]

- **Where:** `Client/addons/client.cpp:290-294`. A `recvfrom` error hits `continue` with no sleep.
- **Impact:** A socket error while `IsConnected` is still true spins a core.

### C15. Partial sends are treated as failures · Low · [Read]

- **Where:** `Client/addons/client.cpp` `SendJsonMessage` compares `send`'s return against the full length.
- **Impact:** A partial write is reported as failure, and the stream is left half-written.
- **Fix:** Loop until the full buffer is sent.

### C16. Launcher and DLL initialization can deadlock · High · [Inferred]

- **Where:** `Client/main.cpp:18-20` spins in `DllMain` until `d3d9.dll` is loaded, while holding the loader lock. `Client/main.cpp:22-38` also performs settings I/O and `MessageBoxA` inside `DllMain`. The launcher waits only for `openal32.dll` (`Launcher/main.cpp:29`), then waits `INFINITE` on the remote `LoadLibrary` thread (`Launcher/main.cpp:66`).
- **Impact:** If the game loads `d3d9.dll` after injection, the game's loader blocks on the loader lock that `DllMain` holds, and the launcher waits forever. Whether this happens depends on the game's load order, which was not checked.
- **Fix:** Move initialization out of `DllMain` (into a thread started from it), and add timeouts to the launcher's waits.

### C17. Launcher over-privileged and leaky · Low · [Read]

- `Launcher/main.cpp:17` opens the game with `PROCESS_ALL_ACCESS`. Least privilege would be `CREATE_THREAD | VM_OPERATION | VM_WRITE | VM_READ | QUERY_INFORMATION`.
- `Launcher/main.cpp:5` enables `SeDebugPrivilege`, which is needed only for processes owned by other users.
- `Launcher/main.cpp:19` and `34` call `TerminateThread` on the dialog thread, leaking its resources. `main.cpp:92` calls `exit(0)` from that thread.
- `Launcher/main.cpp:122` allocates `new wchar_t[MAX_PATH]` and never frees it. `main.cpp:126` silently truncates paths longer than `MAX_PATH`.

### C18. Hooking is unsafe under concurrency · Medium · [Read]

- **Where:** `Client/hook.cpp:127-144` (`SetJMP`) and `hook.cpp:146-216` (`TrampolineHook`) rewrite live code with no thread suspension and no `FlushInstructionCache`. `hook.cpp:238` (`VirtualFree(original)` in `UnTrampolineHook`) can free a trampoline that another thread is still executing. `hook.cpp:240` assigns `original = nullptr` to a local parameter, which does nothing.
- **Also:** `Client/engine.cpp:316-336` installs hooks from a detached polling thread while the game is running.
- **Fix:** Install hooks before the game threads start, or suspend them while patching. Flush the instruction cache after patching. Do not free a trampoline until no thread can be inside it.

### C19. Dolly loaders trust file contents · Medium · [Read]

- **Where:** `Client/addons/dolly.cpp:553-564` (`LoadRecordings`: `Frames.resize(frameCount)` with no bound). `dolly.cpp:502-505` (`LoadMarkers`: `markerCount` loop, read results unchecked). The format has no magic number, version, or endianness.
- **Impact:** A corrupt or hand-made file can trigger `bad_alloc`, or an effectively endless loop. Recordings are user-generated, so this matters if they are shared.
- **Fix:** Check that counts are plausible relative to the file size, check every read, and add a header with a version.

### C20. Game code left writable and executable; cleanup is a no-op · Medium · [Read]

- **Where:** `Client/addons/dolly.cpp:834` changes the protection of the game code page to `PAGE_EXECUTE_READWRITE`. `oldProtect` is never used to restore it. `dolly.cpp:803-812` (`~Dolly`) has its cleanup commented out, with the comment "IF I REMOVE THIS FUNCTION, THE GAME CRASHES ON EXIT". `Client/main.cpp:42-45` destroys every addon immediately after `Initialize`.
- **Impact:** A writable and executable code page is a weaker memory posture. The destructor does nothing, and its comment misleads the next maintainer.
- **Fix:** Restore protection after patching. Replace the superstition with an explanation, or remove the destructor.

### C21. Chaos effects: off-by-one index and unchecked cast · Medium · [Verified by reading the RNG]

- **Where:**
  - `Client/addons/chaos/effects/teleport.cpp:54`: `aicontrollers[RandomInt(0, aicontrollers.Num())]`. `RandomInt` wraps `std::uniform_int_distribution<int>(min, max)` (`effect.cpp:10-14`), which is inclusive on both ends. So the index can equal `Num()`, one past the end.
  - `Client/addons/chaos/effects/killbots.cpp:22`: `static_cast<Classes::ATdSPGame*>(world->Game)` with no type check. On a non-single-player game this is undefined behavior.
  - `Client/addons/chaos/effects/forcerandomdirection.cpp:45`: `RandomInt(0, 65536)` can yield 65536, which wraps.
- **Fix:** Use `RandomInt(0, Num() - 1)`. Check the game's class before casting (`IsA`-style check). Use `RandomInt(0, 65535)`.

### C22. Unchecked game pointers during transitions · Medium · [Read]

- `Client/addons/trainer.cpp:373` (`pawn->WorldInfo->RealTimeSeconds`) and `:395` (`pawn->WorldInfo->TimeDilation`).
- `trainer.cpp:561`: `tdhud->EffectManager->ReactionTimeEffect->bIsActive`, where `tdhud` comes from an unchecked `static_cast` of `controller->myHUD`. Also in the state-load path, `trainer.cpp:574` (`world->Game->GameSpeed`).
- `trainer.cpp:1652` (`controller->PlayerInput->Jump()`), with only `controller` checked.
- `Client/engine.cpp:724` (`world->Game->GetName()`).
- `Client/addons/dolly.cpp:666` (`pawn->Mesh3p->LocalAtoms`).
- **Impact:** These run during level loads and deaths, when these objects can be null. A crash there is user-visible.
- **Fix:** Check each link in the chain.

### C23. Float timestamps lose precision with uptime · Low · [Read]

- **Where:** `Client/addons/chaos/effects/jump.cpp:31`, `63`, `88` store `GetTickCount64()` in a `float`.
- **Impact:** A float has a 24-bit mantissa. At 8.6 × 10⁹ ms (about 100 days of uptime) the resolution is 1 second, so timing error grows with uptime.
- **Fix:** Store as `ULONGLONG` or `double`.

### C24. The "Update Cooldown" button sends the wrong value · Medium · [Read]

- **Where:** `Client/addons/client.cpp:1510-1513` sends `UserClient.CoolDownTag`, which is the last value the server sent (default `5`). The slider value `TagCooldown` (`client.cpp:1503`) is not sent. The announcement at `client.cpp:1515` reports `TagCooldown`.
- **Impact:** The chat says one cooldown was set and the server gets another.
- **Fix:** Send `TagCooldown`.

### C25. Inverted, misleading flag in speedometer loading · Low · [Read]

- **Where:** `Client/addons/trainer.cpp:785-786`. `foundSettings` is assigned `is_null()`, so it is `true` when nothing was saved. The later uses at `787-800` depend on that inverted meaning. `GetSetting` also writes the default into the file (`settings.cpp:55-78`).
- **Fix:** Rename to `hasSavedSettings` and invert the assignment, then re-check the branches.

### C26. Undefined behavior in string handling · Low · [Read]

- `Client/string_utils.h:43`: `std::transform(..., tolower)` passes `char`. Negative values are undefined. Cast to `unsigned char`.
- `Client/addons/client.cpp:1416`: passes `const_cast<char*>(Chat.Raw.c_str())` to ImGui as a writable buffer. The read-only flag prevents writes, but this is still a const violation. Use a copy.

### C27. Per-frame and per-callback cost · Medium · [Read]

- `Client/addons/client.cpp:1050` copies the whole chat log every frame, then measures it (`:1070`). Cost grows with chat history.
- `client.cpp:1613-1647`: `OnActorTick` and `OnBonesTick` loop over every player for every actor or bone callback, taking a lock each time.
- `client.cpp:1627`: `GetBoneLocation("Neck", 0)` does a name lookup on every call.
- **Fix:** Cache the chat layout, index players by actor or ID, and cache bone indices.

### C28. Input and network state from the wrong thread · Medium · [Read]

- `Client/addons/client.cpp:879` calls `IgnorePlayerInput` on the network thread, and `Engine::BlockInput` runs from the input callback. Both write game controller state from a thread the game does not own. This is the same class of problem as C6.

### C29. Crash handler blocks the game · Low · [Read]

- `Client/debug.cpp:138` calls `exit(1)` after `_getch()` waits for a key press. The exception-filter hook also refuses other crash handlers. This is a design choice, but it should be documented.

### C30. Hard-coded server endpoint · Low · [Read]

- `Client/addons/client.cpp:108` resolves the literal `176.58.101.83`. `getaddrinfo` on a literal address does no lookup, so the call is pointless. The endpoint cannot be changed without a rebuild, so self-hosting requires a fork.
- **Fix:** Make it a setting with a sensible default.

### C31. Threads are detached and never stopped · Low · [Read]

- `Client/addons/client.cpp:1715` and `Client/engine.cpp:316-336` detach threads with no shutdown path. Those threads can touch game objects after the game begins tearing down.

### C32. Pattern scanning (positive, with notes) · Info · [Verified]

- All 11 `FindPattern` call sites with literal masks (`engine.cpp`, `trainer.cpp:1720`, `dolly.cpp:826`) have matching byte and mask lengths.
- `Client/pattern.cpp:34-44` scans byte by byte, which is O(image size × pattern length) per pattern. It runs once at startup, so it is acceptable.

## 5. Installer, build, and CI

### B1. The installer evades antivirus and adds an exclusion · High · [Read]

- **Where:**
  - `package.sh:15-16` and `resources/installer/xor/main.go:36` XOR-encode `Launcher.exe` and `mmultiplayer.dll` with key `4`. The source comment in `resources/installer/squibbles/main.go:1-3` says the purpose is to "evade Windows Defender".
  - `resources/installer/squibbles/main.go:107-115` runs `Add-MpPreference -ExclusionPath` on the install directory at install time. The uninstaller removes it (`main.go:158-166`).
- **Impact:** The installer deliberately reduces the protection that antivirus gives to the whole `bin` directory, and the obfuscation is an antivirus-evasion technique. Process injection, obfuscation, and a new AV exclusion are the same signals scanners use to flag malware, so the installer will look that way to scanners and to users.
- **Recommendation:** Sign the binaries with Authenticode, submit false-positive reports to the major vendors, and drop the XOR step and the exclusion. If the exclusion stays, make it an explicit, documented opt-in.
- **Note:** This is a trade-off the maintainers chose. It is flagged because it weakens users' security, not as a bug.

### B2. Packaging expects output paths the build does not produce · Medium · [Inferred]

- `build.sh:10` and `:14` build `Client/` and `Launcher/` with no `OutDir`. Neither `.vcxproj` sets `OutDir` (only the VS Code task does, `.vscode/tasks.json`). Output lands under `Client/Release/` and `Launcher/Release/`.
- `package.sh:15-16` reads `Release/Launcher.exe` and `Release/mmultiplayer.dll` relative to the repo root.
- **Impact:** The packaging step is likely to fail in CI. Verify against a CI log.

### B3. CI supply chain and deprecations · Medium · [Read]

- `.github/workflows/build.yaml:31`: `DXSDK_Jun10.exe` is downloaded with `curl` and never checked against a hash.
- `build.yaml:11`: `contents: write` applies to every job triggered by any push.
- Actions are pinned to tags, not SHAs: `actions/checkout@v3`, `microsoft/setup-msbuild@v1.3.1`.
- `build.yaml:60`: `actions/upload-artifact@v3`. GitHub has deprecated v3 of this action. Verify whether the step still runs.
- `build.yaml:66`: `actions/upload-release-asset@v1` is unmaintained. Replace with `gh release upload` or a maintained action.
- `build.yaml:74`: `asset_content_type: 'application/x-tar'` for an `.exe`. Use `application/octet-stream`.
- `build.yaml:23`: `runs-on: windows-2019`. GitHub has deprecated this runner image. Verify.

### B4. Minor installer issues · Low · [Read]

- `resources/installer/squibbles/main.go:117` and `:123` open files with `O_CREATE|O_WRONLY` and no `O_TRUNC`. If an existing file is longer, stale bytes remain. `[InstallDelete]` in `installer.iss` mitigates this on reinstall.
- `resources/installer/squibbles/main.go:107-115` builds a PowerShell argument from the install path. The path is fixed by `DisableDirPage=yes`, so the risk is low, but the path should be passed without shell interpretation.

### B5. Build configuration inconsistencies · Low · [Read]

- `Client/Client.vcxproj:64` sets `stdcpp20` for Debug, while `:84` sets `stdcpp17` for Release.
- `CONTRIBUTING.md` says Visual Studio 2019, while `.vscode/tasks.json` points at the 2022 BuildTools path.

### B6. No automated tests or static analysis in CI · Medium · [Read]

- CI only builds. There is no Go test, no `go vet`, no race detector, and no C++ static analysis or sanitizer build. The server findings above (S1, S2) would have been caught by `go test -race`.
- Positive: `go vet ./Server` and `gofmt -l` are clean.

## 6. Accessibility (in-game UI)

### A1. Colour is the only signal for the tagged player · Medium · [Read]

- **Where:** `Client/addons/client.cpp:1008-1015`, `1184-1186`. The tagged player's name tag is red and nothing else marks them. Colour-blind players may not tell red from white.
- **Fix:** Add an icon or text marker (for example "IT") in addition to colour.

### A2. Chat and menu are keyboard and mouse only · Medium · [Read]

- **Where:** Chat opens on `WM_KEYDOWN` (`Client/addons/client.cpp:1586-1593`). The menu toggles on `WM_KEYUP` (`Client/menu.cpp:218-230`). No gamepad input path was found.
- **Impact:** Players using a controller cannot open chat or the menu without a keyboard.

### A3. Legibility and text scaling · Low · [Read]

- `Client/engine.cpp:110` loads a fixed 16-pixel Verdana from `C:\Windows\Fonts`. There is no scaling option, and the path is hard-coded (`%SystemRoot%` would be correct).
- Name tags and the chat overlay sit on 40 % black backgrounds (`client.cpp:1006`, `1076`). Contrast on bright scenes was not measured. Needs testing.
- The chat overlay fades to transparent after 5 seconds (`client.cpp:1034-1043`) with no option to keep it visible.

### A4. Good practice found · Positive

- The hotkey widget shows "<Press a key>" while waiting and clears on Escape (`Client/imgui/imgui_mmultiplayer.cpp:424-445`).
- Help markers provide tooltips (`imgui_mmultiplayer.cpp:464-474`).
- Mouse buttons are supported as bindings (`imgui_mmultiplayer.cpp:392-404`).

### A5. Chat input limits are invisible · Low · [Read]

- `ChatInput` holds 511 characters (`client.cpp:1419`) with no counter. The server accepts messages of any length (S4).

## 7. Performance (consolidated)

- **Server:** O(N) lookup per UDP packet, per-packet goroutine, and per-peer syscalls under a lock (S1, S18). Per-recipient goroutines per message (S5, S6).
- **Bandwidth:** Each client sends about 40 KB/s and receives (N − 1) × 40 KB/s. The server fan-out is O(N²) in total traffic (S18).
- **Client:** Per-frame chat copy and measure (C27). Per-actor and per-bone lock and scan (C27). Name-based bone lookup each call (C27).
- **Settings:** Full-file rewrite on every read (C12).

## 8. Code quality and maintainability

- **Q1. Oversized header.** `Client/addons/trainer.h` is 2,759 lines with inline implementations. Move implementations to a `.cpp`.
- **Q2. `static` definitions in headers.** `Client/addons/client.h:12` (`CompressedBoneOffsets`), `util.h`, and `string_utils.h` define `static` data and functions in headers, so each translation unit gets its own copy.
- **Q3. Warnings suppressed wholesale.** `#pragma warning(disable: 26495)` in `engine.cpp:13`, `client.h:3`, and `trainer.h:4` hides "uninitialized member" warnings. That is the category behind C2 and C25.
- **Q4. Global mutable state with no ownership model.** Statics in `client.cpp`, the settings JSON, the chaos RNG, and engine hook structs. This is the root cause of most of C3–C7.
- **Q5. Magic numbers.** Buffer sizes `0xFF` and `0x200`, the packet size `676`, the bone scale `215.f`, tick thresholds `0.016f` and `0.16f`, the tag radius `1.3` m, the default cooldown `5` s, and the status timeout `5000` ms. None are named, and the server does not share them.
- **Q6. Manual lock and unlock.** `Chat.Mutex.lock()`/`unlock()` (`client.cpp:1048-1084`, `1415-1417`) and `Players.Mutex` sequences are not exception-safe. Settings and `json` code throws in these paths. Use RAII guards.
- **Q7. Misleading names.** `foundSettings` (`trainer.cpp:785`). `RandomInt(0, 65536)` (`forcerandomdirection.cpp:45`).
- **Q8. Logging.** `printf` everywhere with no levels. Server logs contain unescaped client input (S14).
- **Q9. Commented-out code and superstitions.** `dolly.cpp:803-812` (see C20). `hook.cpp:240` (dead assignment).
- **Q10. Server style.** Package-level `system` global, with a receiver named `system` in `system.go` that shadows it. Dead code (S17).
- **Q11. Protocol documentation.** The wire protocol is undocumented and unversioned (S22).
- **Q12. No automated tests** on either side (B6).

## 9. What is working well

- **Server:** `go vet` and `gofmt` are clean. Character indices are range-checked (`client.go:58-61`, `176-179`). Names are trimmed (`client.go:263-266`). Locks are used consistently in most paths, which is why the two deadlocks above are narrow.
- **Client:** The UDP packet size matches the server's constant (676 bytes). All 11 pattern and mask pairs are length-consistent (C32). The hotkey widget bounds-checks its key index (`imgui_mmultiplayer.cpp:327-330`). Many game-pointer accesses are guarded (for example `client.cpp:904-905`, `1627`, and `dolly.cpp`'s init path). Chaos seeding is wired correctly end to end (`chaos.cpp:56`, `61`, `82`, `640`).

## Appendix: How the server results were produced

- Copy of `Server/` placed in a scratch directory outside the repo. `go mod download github.com/google/uuid@v1.3.0` succeeded.

- All 11 `FindPattern` byte and mask pairs were compared programmatically. All match.
